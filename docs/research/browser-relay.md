# Browser relay and assisted publishing

Research snapshot: 2026-11-21. This is a technical and policy assessment, not legal advice. `[UNVERIFIED]` means the primary sources reviewed do not establish the point. See also [platform APIs](platform-apis.md) and [existing tools](existing-skills-and-tools.md).

## Decisions

1. **Default to manual browser handoff, not browser automation.** `mblast publish --assist` should open an official share/compose URL where available and offer copy for the person to paste, review and post. A platform-provided prefilled share URL is different from a script driving its site. There is no zero-ban-risk guarantee: content, behavior and account enforcement still matter.
2. **HN is strictly manual and human-authored.** No generated text, automated form filling, relay or automated posting. `mblast` may only print the original article URL and original title; the person decides whether to submit, writes any accompanying text, and enters and submits it themselves. HN explicitly says not to put generated text in posts and not to automate posting. [HN guidelines](https://news.ycombinator.com/newsguidelines.html)
3. **Do not script LinkedIn, X or Threads, even with a human final click.** LinkedIn prohibits unauthorized automated access and post actions; X specifically warns against non-API website scripting; Threads incorporates Instagram's prohibition on unauthorized automated access. User consent or a manual last click does not itself authorize preceding scripts. Use official share flows and manual input, or an authorized API/integration. [LinkedIn](https://www.linkedin.com/legal/user-agreement#dos), [X](https://help.x.com/en/rules-and-policies/x-automation), [Threads](https://www.facebook.com/help/instagram/769983657850450), [Instagram](https://www.facebook.com/help/instagram/termsofuse)
4. **Relay-assisted fill is a conditional design, not the default or an existing mblast feature.** Only consider it per platform after explicit platform permission has been established; otherwise use manual handoff. If allowed, prefer omp relay in an existing omp session, with manual paste as the immediate fallback. Playwright MCP extension is a possible alternative, not a reason to expand the trust boundary by default. Generic Node CLI integration with omp's Eval-only browser facade is **[UNVERIFIED]**; `omp browser-relay install` is an installer, not a documented standalone mblast browser-control API. Do not promise a native integration before a supported interface is established. [omp browser](omp://tools/browser.md), [Playwright extension](https://github.com/microsoft/playwright/tree/main/packages/extension)
5. **Final publish remains a physical user decision.** Track an unconfirmed handoff separately from a confirmed published post; request the resulting permalink from the person unless a platform-authorized way of reading it exists. Never mark success just because the compose page opened or a draft was filled.

## Mechanism comparison

Risk refers to exposure and policy risk, not a ranking of detection probability; the site and action determine actual policy. None is intrinsically ToS-safe.

|---|---|---|---|

| omp relay | Chrome retains its own profile, cookies and logins; an assisted design need not export credentials to mblast. | Install extension and native host; connect a running Chrome and use omp Eval browser with `app: "relay"`. | Full browser control is powerful: helpers can read cookies and page data, export state, run JS, fill and click. Avoid unnecessary agent and third-party session access. [browser-use](https://github.com/browser-use/browser-use) |

### Session and credential security

Chrome on macOS uses a Keychain-backed Safe Storage secret for its encryption machinery; Chrome cookies and profile files are not equivalent to a portable plaintext `storageState` JSON. Details vary by browser/build and data type: **[UNVERIFIED]** that every profile artifact is encrypted. Keychain encryption does not protect against a trusted extension, an attached debugging client, a compromised unlocked user session, or an exported JSON. Chrome explicitly documents remote debugging being abused to extract cookies. [Chromium keychain source](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/os_crypt/common/keychain_password_mac.mm), [Chrome](https://developer.chrome.com/blog/remote-debugging-port), [Playwright auth warning](https://playwright.dev/docs/auth)

Use a trusted local machine, OS account and full-disk encryption; restrict profile and state files to the user, never commit them, and avoid cookie dumps, HARs, screenshots or debug logs containing private data. Persistent storage is not permanent authorization: sites expire/revoke sessions or demand reauthentication. The human completes password, passkey, 2FA and CAPTCHA directly in the browser; mblast should not collect credentials, bypass challenges, or infer that a saved cookie avoids future 2FA. [Playwright authentication](https://playwright.dev/docs/auth)

### omp relay specifics

`omp browser-relay --help` describes `install`, `sync`, and `native-host` (the latter launched by Chrome). `omp browser-relay install` installs/syncs the Chrome extension and registers its native host; `--profile` selects the Chrome profile and `--no-chrome` prints manual steps. The default extension directory is `~/.omp/browser-relay/extension`. Follow installer output and, when required, load the unpacked extension in `chrome://extensions`; run `sync` to update registered extension directories. This bridges omp's local browser driver through the extension/native host to the user's real Chrome profile, where the existing signed-in sessions remain. It avoids a separate mblast credential store **by design**, not because the bridge is technically incapable of reading secrets. [CLI reference](omp://cli-reference.md), [omp browser](omp://tools/browser.md)

Within omp Eval, `browser.open({name, app: "relay", url, persist: true})` opens an omp-owned background tab in real Chrome; `observe`, `fill`, `type`, `click`, `goto`, `evaluate`, URL and waiting helpers can drive and inspect it. `persist: true` keeps an opened relay tab after the session ends for the person; otherwise it closes. `browser.targets({app: "relay"})` discovers existing tabs; `target` borrows a real user tab and must never navigate it without explicit authorization. Do not infer a successful site action merely from a tool call. An old extension may select the user's tab rather than opening a background tab; reconnects, cross-origin frames, native dialogs, changed editors, page state, and extension permissions can prevent reliable filling. Relay tabs cannot select a download directory. Browser actions require exec-tier approval. [omp API](help://eval/browser), [omp browser documentation](omp://tools/browser.md)

A normal Node `mblast` process does not automatically inherit omp Eval's `browser` object. A bridge between CLI and omp, including lifecycle and permission boundaries, remains **[UNVERIFIED]**; until documented and implemented, manual handoff is the deployable default. MCP extension likewise requires a compatible MCP client or separately implemented client integration. Neither is an official platform API.

For every destination, an automated final submit increases the number of consequential actions delegated and duplicate/spam risk; where underlying automation is prohibited, a human final click does not cure the initial violation. Do not use stealth, artificial delays, profile copying or CAPTCHA bypass to evade detection. API availability, platform permission, product pricing and content policies are separate decisions.

## Proposed assisted workflow

This is a proposed interface, not a claim about current CLI behavior.

1. `mblast publish --assist` presents one destination at a time, its actual copy/link, platform constraints and proposed handoff. HN is special: show only the original title and original URL; no generated HN content or automated submission. The person chooses the destination and may skip it.
2. For non-HN targets, open the platform's documented share/compose URL in the user's normal browser, with supported URL parameters only; otherwise open its editor and provide copy for manual paste. Do not claim a field was populated without evidence. Never use arbitrary scripts, CDP, or DOM reads on LinkedIn, X, Threads, HN or other destinations lacking established permission. For long-form editors the user handles formatting, media, canonical, audience and email/scheduling settings.
3. **Only if platform permission for automated access/fill is confirmed:** an opt-in omp session could use a new `persist: true` relay tab to inspect the visible editor, fill title/body/link as appropriate, read values back, then stop. No navigation of a borrowed tab without consent; no hidden form mutation or synthetic submit. If no supported Node-to-omp integration exists, use manual copy/paste. Disable automation by default; permission is not inferred from user consent.
4. The person reviews, changes and physically clicks every required Post/Publish/Send confirmation; the program never clicks or invokes a submit endpoint. A cancel or scheduled/draft choice is not a publication. A human click is an accountability control, not a ToS exemption.
5. Ask the person to copy the actual post's permalink into `mblast` after publication. Validate HTTPS and an appropriate platform host, display it back for confirmation, and write the confirmed URL to the existing `state.json` using its actual schema via the existing mark mechanism, not a newly invented schema. Do not store a compose URL, generic feed URL, redirect to another host, or scheduled draft as a published permalink. If no permalink is available or the user skips, retain pending/unconfirmed status and allow later manual marking. **[UNVERIFIED]** whether every site exposes an immediately shareable URL. Where platform permission explicitly permits reading post-submission page state, a candidate URL can be offered for confirmation, but never required.

**Failure handling:** Login expiry, 2FA, wrong profile/account, disabled extension, browser detach, changed selectors, restricted frames, editor-specific formatting, unavailable compose URL, and closed tabs all result in a visible handoff/pending status, not a retry that might post twice. The person resolves login or challenge; on uncertain submission they inspect their account before retrying. If URL capture/marking fails after a successful post, preserve the unconfirmed state and let the person supply the permalink later. Avoid logging full editor content, query strings with sensitive copy, cookies or authorization headers; clear clipboard only when safe and with user awareness.

### One-time local setup

1. Sign in to each desired destination in the user's normal browser and enable the platform's 2FA; complete challenges personally. No mblast password, cookies or exported browser state in the repository. For HN use the original article and manually authored text only.
2. For the default manual workflow, ensure the default browser opens links and clipboard access is available. No extension, native host, API token, MCP server or debug port is required.
3. Only for a destination with explicit authorization for relay-assisted fill and an actual supported integration: install omp and Chrome; run `omp browser-relay install` (optionally `--profile <Chrome-profile-directory>`), follow its installation output, and use `chrome://extensions` Load unpacked if needed. Keep Chrome running in that profile; enable/select relay in omp or explicitly select `app: "relay"`. `omp browser-relay sync` updates installed extension directories. Grant only trusted local sessions browser control. [omp](omp://tools/browser.md), [CLI help](omp://cli-reference.md)
4. Alternative only when an MCP client is intentionally used and policy permits: install [Playwright Extension](https://github.com/microsoft/playwright/tree/main/packages/extension), configure `@playwright/mcp --extension`, and approve the client and tabs. Do not put the optional extension auto-connect token in a repository. If relay/MCP fails or is not authorized, return to manual paste—not another automation mechanism.
5. After each actual publication, copy its permalink and use the CLI's existing mark flow; set up official API access separately only for platforms where that is desired and authorized.
